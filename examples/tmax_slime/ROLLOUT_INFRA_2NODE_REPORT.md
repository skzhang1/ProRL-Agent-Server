# Polar + Slime 2-node rollout infrastructure report

Date: 2026-07-22/23 (NRT)

## Result

The rollout-only acceptance run completed all 8 rollout steps at the target load of 8 prompt groups x 32 samples (256 trajectories per step). The run used the current project's Polar and the friend's Slime. It used two non-reserved interactive nodes, one gateway per node, and all 16 GPUs for rollout.

The eight durable boundaries are complete and contiguous:

- `debug_rollout_0.pt` through `debug_rollout_7.pt`
- `rollout/global_dataset_state_dict_0.pt` through `rollout/global_dataset_state_dict_7.pt`

The final allocation, Slurm job `5364556`, ended naturally with `COMPLETED (0:0)`. No gateway restart or Slurm OOM occurred. Both gateway logs contain the complete application shutdown sequence.

## SIGKILL investigation

SIGKILL was investigated rather than bypassed or hidden by lowering load.

The final allocation added 13 code-137 sessions. All 13 trajectories contain broad process-kill commands generated by the agent, including examples such as:

- `pkill -9 -u root`
- `pkill -9 -f python`
- `pkill appinit`
- loops over `/proc` followed by `kill -9` or `os.kill(pid, 9)`

Representative live evidence showed the supervised shell and PI process disappear immediately after these commands. At the same time, the node cgroup reported `oom=0` and `oom_kill=0`, with roughly 1.8 TB available memory. The gateway continued serving other sessions and each rollout batch completed.

Root cause: these are agent-induced self-SIGKILL events inside the session PID namespace, not Slurm OOM and not accumulated orphan processes. A raw `apptainer exec` process tree gives these commands a less reliable teardown boundary. Instance mode plus `--containall` keeps the failure inside one session and gives Polar a named object to stop afterward, so it is the recommended mode.

One `instance stop ... no instance found` warning occurred after an agent killed its own `appinit`; the instance had already exited. It did not leave a running instance or affect the gateway. This is kept as a visible per-sample failure rather than masked with a fallback.

The supervised inner shell now writes its exit status from an `EXIT` trap. This distinguishes a wrapper killed during teardown from a genuine inner SIGKILL: a real group SIGKILL has no status file and remains code 137, while an orderly inner SIGTERM preserves code 143 instead of being misreported as 137.

## Other observed errors

The final allocation logged three transient SGLang router send failures to individual workers. They occurred at different times, were absorbed by the existing task/replacement path, caused no gateway restart, and did not prevent the affected rollout step or checkpoint from completing. No additional retry/fallback layer was added.

Oversized or empty traces were dropped by the existing adapter and replaced with dummy placeholders as designed. This affects efficiency and sample usability, but it did not destabilize the infrastructure.

## Minimal implementation changes

The changes are limited to the rollout launcher and the Polar lifecycle paths required by the observed failures:

- Added an independent two-node rollout-only submission script with durable step-by-step resume.
- Plumbed `polar_max_steps`, rollout-only mode, node-rank gateway routing, and the tested worker limits through the existing launcher.
- Added the simple max-step check alongside the existing timeout check; whichever triggers first terminates the session.
- Made session cancellation terminate the whole runtime process group, including detached descendants.
- Added Apptainer instance mode, optional PID isolation, and supervised exit-status recording.
- Preserved nested child-session routing to the parent's gateway.
- Kept PI configuration/session temporary files inside the session and passed gateway headers/API key correctly.

No change was made to `submit_tmax_pi_4node_reference_recipe.sh`.
